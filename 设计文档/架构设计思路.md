# AgentCritic 架构设计思路

> 给 LLM 应用装「裁判」——让 AI 效果从拍脑袋变成可量化、可对比、可回归的工程问题。
> 配套：Travel-Hub（造 Agent 的引擎）→ AgentCritic（评 Agent 的裁判）

## 分层说明

| 层 | 职责 | 关键点 |
|----|------|--------|
| **输入层** | 评测从哪来 | 手工测试集（先跑通）+ Travel-Hub 日志适配器（M3 再自动化）+ 触发入口 |
| **评测引擎** | 核心编排 | Evaluator 逐条执行 TestCase，通过适配器调被测对象，收集结果与失败归因 |
| **Judge 裁判层** | 三种打分 | LLMJudge（主观质量）/ RuleJudge（客观格式）/ MetricJudge（检索指标计算） |
| **被测对象** | Travel-Hub 三件套 | 编排引擎 / RAG 多路召回 / 模型——每个评测面都有真实案例 |
| **基础设施** | 支撑 | 测试集 Git 管理、评测历史可回归对比、Judge 用的 LLM |
| **输出** | 结果落地 | 报告（JSON/MD/HTML）+ 多版本/多模型对比看板 |

## 关键设计决策

```
① 适配器隔离：被测对象适配器（Model/Rag/Agent）是唯一接触外部的边界——
   换被测系统只改适配器，评测引擎不动
② Judge 三态分离：主观（LLM）+ 客观（规则）+ 数值（指标）各管一摊，
   LLMJudge 只花在该花的 token 上
③ 结果回流：被测对象执行结果回到 Evaluator 做失败归因——
   「哪一步挂的、召回空还是格式错」是最能体现评测系统价值的能力
```

## 路线图对照

```
M1：手工测试集 → TestSuite 管理器 → 被测对象适配器（RAG）→ MetricJudge → LLMJudge → Markdown 报告
                                                              ✅ 第一版最小闭环
M2：+ 被测对象适配器（Agent）→ 成功率 + 失败归因                ✅ Agent 评测
M3：+ 日志适配器自动抽样本                                      ✅ 数据自动化
M4：+ 多模型对比 → 对比看板                                      ✅ 模型选型
```

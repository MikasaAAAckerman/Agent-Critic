# AgentCritic 架构图

> 给 LLM 应用装「裁判」——让 AI 效果从拍脑袋变成可量化、可对比、可回归的工程问题。
> 配套：Travel-Hub（造 Agent 的引擎）→ AgentCritic（评 Agent 的裁判）

---

## 总体架构

```mermaid
graph TD
    %% ═══════════════ 输入层 ═══════════════
    subgraph IN[输入层]
        A1[手工测试集<br/>TestSuite / TestCase<br/>YAML or JSON]
        A2[Travel-Hub 日志适配器<br/>消费 llm_call_log / traceId<br/>自动抽评测样本]
        A3[触发入口<br/>CLI / API / 定时回归]
    end

    %% ═══════════════ AgentCritic 核心 ═══════════════
    subgraph CORE[AgentCritic 评测引擎]
        B1[评测编排器 Evaluator<br/>逐条执行 TestCase<br/>收集结果 + 归因]
        B2[被测对象适配器<br/>ModelAdapter / RagAdapter / AgentAdapter]
        B3[TestSuite 管理器<br/>加载 / 去重 / 版本]
        B4[Judge 工厂<br/>按 Metric 类型路由]
        B5[Metric 计算器<br/>检索指标 / 成功率统计]
        B6[报告生成器<br/>JSON / Markdown / HTML]
    end

    %% ═══════════════ Judge 三态 ═══════════════
    subgraph JUDGE[Judge 裁判层]
        C1[LLMJudge<br/>忠实度 / 相关性 / 正确性<br/>LLM-as-Judge]
        C2[RuleJudge<br/>格式校验 / 关键词 / JSON Schema]
        C3[MetricJudge<br/>Recall@K / MRR / NDCG<br/>规则计算]
    end

    %% ═══════════════ 被测对象 ═══════════════
    subgraph TARGET[被测对象 · Travel-Hub]
        D1[编排引擎<br/>多 Agent Graph]
        D2[RAG 多路召回<br/>PGVector + ES BM25]
        D3[LLM 模型<br/>DeepSeek / Qwen / 其他]
    end

    %% ═══════════════ 基础设施 ═══════════════
    subgraph INFRA[基础设施]
        E1[测试集存储<br/>Git 管理 / JSON]
        E2[评测历史库<br/>PG / 本地文件]
        E3[Judge 用 LLM<br/>qwen / deepseek / claude]
    end

    %% ═══════════════ 输出 ═══════════════
    F1[评测报告<br/>分数对比表 / 回归趋势]
    F2[对比看板<br/>多模型 / 多版本对比]

    %% ── 流向 ──
    A1 --> B3
    A2 --> B2
    A3 --> B1

    B3 --> B1
    B1 --> B2
    B2 --> D1
    B2 --> D2
    B2 --> D3

    B1 --> B4
    B4 --> C1
    B4 --> C2
    B1 --> B5
    B5 --> C3

    C1 --> E3
    C1 --> B1
    C2 --> B1
    C3 --> B1

    D1 --> B1
    D2 --> B1
    D3 --> B1

    B1 --> B6
    B6 --> F1
    B6 --> F2
    E1 --> B3
    E2 --> B1
```

## 分层说明

| 层 | 职责 | 关键点 |
|----|------|--------|
| **输入层** | 评测从哪来 | 手工测试集（先跑通）+ Travel-Hub 日志适配器（M3 再自动化）+ 触发入口 |
| **评测引擎** | 核心编排 | Evaluator 逐条执行 TestCase，通过适配器调被测对象，收集结果与失败归因 |
| **Judge 裁判层** | 三种打分 | LLMJudge（主观质量）/ RuleJudge（客观格式）/ MetricJudge（检索指标计算） |
| **被测对象** | Travel-Hub 三件套 | 编排引擎 / RAG 多路召回 / 模型——每个评测面都有真实案例 |
| **基础设施** | 支撑 | 测试集 Git 管理、评测历史可回归对比、Judge 用的 LLM |
| **输出** | 结果落地 | 报告（JSON/MD/HTML）+ 多版本/多模型对比看板 |

## 关键设计决策

```
① 适配器隔离：被测对象适配器（Model/Rag/Agent）是唯一接触外部的边界——
   换被测系统只改适配器，评测引擎不动
② Judge 三态分离：主观（LLM）+ 客观（规则）+ 数值（指标）各管一摊，
   LLMJudge 只花在该花的 token 上
③ 结果回流：被测对象执行结果回到 Evaluator 做失败归因——
   「哪一步挂的、召回空还是格式错」是面试最想听的归因能力
```
